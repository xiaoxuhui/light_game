### 签名实证

线上 APK 的签名证书与仓库里那把固定 keystore **逐字节相同**：

| 来源 | 证书 SHA-256 指纹 |
|---|---|
| 线上 APK（APK Signing Block v2） | `89:E5:2B:69:7A:A5:EA:1E:34:D4:6C:D8:09:71:62:30:A6:3F:B9:C0:A3:FC:FE:6C:3C:73:86:AE:EC:53:C2:D6` |
| `android/app/debug.keystore` | `89:E5:2B:69:7A:A5:EA:1E:34:D4:6C:D8:09:71:62:30:A6:3F:B9:C0:A3:FC:FE:6C:3C:73:86:AE:EC:53:C2:D6` |

两个 DER 证书用 `cmp` 比对完全一致 → **构建机确实用了仓库里这把签名**，
不再是从前那种「每台机器现生成一把随机 key」的状态。

> **一个容易误判的点**：这个 APK 的 `META-INF/` 里**没有** `CERT.RSA` / `CERT.SF` / `MANIFEST.MF`。
> 这不是没签名 —— `minSdk = 24` 时 AGP 会自动跳过 v1（JAR）签名，
> 证书只存在于 APK Signing Block 的 v2 方案里。要核对签名就别在 `META-INF/` 里找，
> 得解析签名块（脚本思路见下方附录）。

## 3. 待真机确认

### 3.1 U23 覆盖升级（本轮最该验的一条）

> ⚠️ 从 **1.1.0 升到 1.2.0 需要先卸载旧版**。1.1.0 是用当年那次构建的**随机签名**发布的，
> 新签名无法覆盖它，系统会直接报「应用未安装」。卸载会清空本地存档（星数、布局、快照）。
> **这是唯一一次需要卸载**：从 1.2.0 起签名固定，之后再升级都能直接覆盖。

1. 装 1.2.0（若手机上还是 1.1.0，先卸载旧的）。
2. 进任意关卡拿一颗星，留点布局。
3. 等我发下一个版本时，直接安装新 APK，**不卸载**。

预期：直接覆盖安装成功，星数与布局都还在。

## 4. 已知限制（属设计取舍，不是缺陷）

| 项 | 说明 |
|---|---|
| debug 签名 | 仍用 debug 签名分发，便于直接安装；代价是部分系统提示「来源不安全」。签名**已固定**，不影响覆盖升级 |
| 存档不互通 | 安卓端 page 跑在 `appassets.androidplatform.net` 的 https 域下，`localStorage` origin 与网页版不同，安卓端存档从零开始 |
| 无物理键盘 | 手机端不提供键盘操作，但所有操作都有触摸等价路径 |
| 导入授权不持久 | 走系统文件选择器，选中文件读完即止，下次需重新选 |

## 5. 附录：怎么自己核对签名

没有 Android 工具链时，用 Python + openssl 就能核，思路：

1. 读 APK 末尾，`rfind(b"APK Sig Block 42")` 定位 magic；
2. 块起始偏移 = `magic 位置 + 8 - magic 前 8 字节的 uint64 值`
   —— 这个 size 值**包含 magic 自身的 16 字节**，算的时候漏掉就会错位 16 字节；
3. 从块起始 +8 顺序读 `uint64 长度 + uint32 ID` 的键值对，取 ID `0x7109871a`（v2）；
4. 逐层剥长度前缀（signers → signer → signed_data → certificates），拿到 DER 证书；
5. 与 keystore 里的证书比对：`openssl pkcs12 -in debug.keystore -passin pass:android -nokeys`。

证书指纹、`versionName`、assets 清单三项一起核，就能确认「线上这个包 = 仓库这份代码 + 这把签名」。
