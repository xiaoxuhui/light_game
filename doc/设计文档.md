# 光的游戏：设计文档

## 文档信息

| 项目 | 内容 |
|---|---|
| 文档版本 | r3（v1.0.0 实现回填） |
| 对应需求 | `需求与测试用例.md` r3 |
| 当前代码状态 | v1.0.0（16 关全量可玩、撤销重做、存档与导入导出齐备） |
| 实施策略 | 单页纯静态应用，先 Web 后 APK；工程结构从第一天起按 APK 约束设计 |

## 一、设计目标

1. **零构建**。仓库根目录即 Web 根目录，双击 `index.html` 就能跑，不依赖任何打包产物。
2. **零运行时依赖**。不引框架、不引工具库，浏览器原生能力优先。
3. **可离线**。所有资源本地化，无 CDN、无接口请求。
4. **规则与渲染分离**。玩法纯逻辑可脱离浏览器单测，渲染层不复制任何规则判定。
5. **为 APK 预留接口**。资源同步、文件导出两条链路从第一天就收敛到单点。
6. **触摸与鼠标同源**。统一用 Pointer Events，不为两套输入写两份逻辑。
7. **高分屏与窄屏都正确**。按 DPR 作画，适配刘海安全区与横竖屏。

## 二、总体形态

```
浏览器侧  index.html + styles/main.css + 若干 <script defer> 脚本（共享全局命名空间）
开发侧    scripts/serve-static.js      零依赖静态服务（仅本地与 e2e 使用，不属于应用）
交付侧    仓库根目录即站点根目录，任意静态托管可跑；安卓打包时整目录同步进 assets
```

**为什么不用 ES Module**：阶段二 WebView 通过
`https://appassets.androidplatform.net/assets/index.html` 加载本地资源，
`file://` 与 module 组合会被 CORS 拦截，且 module 的加载时序对纯离线资源不友好。
多文件 + `defer` 顺序加载是这个场景下最稳的方式。

## 三、模块分层

### 3.1 骨架阶段的形态（历史记录）

v0.1.0 时只有 `scripts/app.js`（引导 + 待机占位渲染）与 `scripts/serve-static.js`，
`app.js` 刻意保持很薄。玩法逻辑按 3.2 拆出去后，它只留编排职责 —— 这个边界在 v1.0.0 里守住了。

### 3.2 模块划分

按 `<script defer>` 依赖顺序（**加载顺序即依赖顺序，不可打乱**）：

| # | 文件 | 职责 | 允许依赖 | 可单测 | 状态 |
|---|---|---|---|---|---|
| 1 | `scripts/light-core.js` | 8 方向常量、颜色掩码、反射与分光规则、元件规则表 | 无 | ✅ | 已实现 |
| 2 | `scripts/light-engine.js` | 光路求解、目标判定、星级计算 | `light-core` | ✅ | 已实现 |
| 3 | `scripts/levels.js` | 内置关卡数据（16 关）+ schema 校验、布局校验、外部关卡注册 | `light-core` | ✅ | 已实现 |
| 4 | `scripts/renderer.js` | 把引擎输出画到 canvas，**不含任何规则判定** | `light-core`（仅取常量） | ❌ | 已实现 |
| 5 | `scripts/storage.js` | `localStorage` 存档、工作台快照、JSON 导入导出、`downloadFile()` | `light-core`、`levels` | ✅ | 已实现 |
| 6 | `scripts/app.js` | 编排：输入 → 引擎 → 渲染 → HUD → 存档 | 全部 | ❌ | 已实现 |

前四个脚本同时支持两种加载方式：浏览器里挂到 `globalThis.LightXxx`，
Node 单测环境通过 `module.exports` 拿到**同一份实现**（UMD 包装，共用一份代码）。
`storage.js` 用同一套包装，因此存档往返与关卡文件解析可以在 Node 里直接测。

分层红线（由 `CONTRIBUTING.md` 与代码评审共同保证）：

- `light-core` / `light-engine` 不碰 DOM、不碰 canvas，输入输出都是普通数据结构。
- `renderer` 不复制规则判定，只读引擎给出的结果。
- `storage` 不碰 DOM（`downloadFile` 是唯一例外，且已收敛为单点），变换函数一律
  **返回新对象、不改入参** —— 这样单测里比较往返结果最省事，也避免存档与画面串味。
- 随机性必须可注入种子（本游戏目前无需随机，保留该约束以备后续）。

新增脚本后必做三件事：

1. `index.html` 按依赖顺序加 `<script defer>`。
2. `eslint.config.js` 的 `crossScriptGlobals` 补上新的跨文件全局，否则 lint 报 `no-undef`。
3. `package.json` 的 `check` 脚本追加 `node --check scripts/新文件.js`。

### 3.3 已实现的骨架链路

| 机制 | 实现要点 |
|---|---|
| 高分屏 | 后备缓冲 = CSS 尺寸 × `devicePixelRatio`，dpr 封顶 2，避免 4K 屏过度绘制 |
| 尺寸跟随 | `ResizeObserver` 观察画布自身，而非监听 `window.resize` |
| 渲染节流 | 单个 `requestAnimationFrame` 循环；`visibilitychange` 隐藏时取消循环 |
| 动效偏好 | 画布没有任何时间驱动的动画（每帧都是静态绘制，静置时脏标记为假、一帧都不画），所以 JS 里没有需要冻结的东西；唯一的动效是按钮过渡，由 CSS 媒体查询关掉。阶段 3 复查时删掉了原先那个只挂 `change` 监听、从不被读取的 `matchMedia` 变量 |
| 坐标系统 | 以设备像素作画（`canvas.width/height` 即物理像素），不做手工 `ctx.scale`，以免将来与网格坐标换算叠加出二层变换 |
| 调试手柄 | `window.__lightGame` 暴露 `start` / `stop` / `resize`，供 e2e 与控制台使用 |

### 3.4 渲染循环与脏标记

骨架阶段的「待机光晕」占位渲染已在阶段 2.3 **整体移除**，替换为真正的场景渲染
（`LightRenderer.drawScene`），没有在原函数上叠加任何功能。

循环用**脏标记**驱动：`requestAnimationFrame` 常驻，但只有 `state.dirty` 为真时才真正绘制一帧。
静置时（没有元件增删、没有指针移动、没有尺寸变化）每帧只做一次布尔判断，几乎不占 CPU。
这与本作「无计时、放松」的定位一致，也让移动端不必为了动画持续唤醒 GPU。

置脏的时机集中在几处：元件增删改、光标／悬停格变化、画布尺寸变化、关卡切换、动效偏好变化。
`window.__lightGame.state.dirty` 因此也成了 e2e 里「等一帧画完」的可靠信号。

## 四、核心算法

### 4.1 方向与颜色

**方向**用 8 个索引表示，顺时针排列，配 `(dx, dy)` 增量（屏幕坐标系，y 轴向下）：

| 索引 | 方向 | dx | dy |
|---|---|---|---|
| 0 | 上 | 0 | −1 |
| 1 | 右上 | 1 | −1 |
| 2 | 右 | 1 | 0 |
| 3 | 右下 | 1 | 1 |
| 4 | 下 | 0 | 1 |
| 5 | 左下 | −1 | 1 |
| 6 | 左 | −1 | 0 |
| 7 | 左上 | −1 | −1 |

**颜色**用 3 位掩码：`R=1, G=2, B=4`。合成即按位或，拆分即按位与。

### 4.2 反射规则（本设计的核心，整数运算无浮点误差）

镜面朝向只有两种：`/` 与 `\`，镜面方向的整数向量分别为 `(1,−1)` 与 `(1,1)`。
对入射方向 `(dx, dy)`，出射方向可由镜像公式化简为**纯整数交换**：

| 镜面 | 出射方向 | 说明 |
|---|---|---|
| `/` | `(−dy, −dx)` | 分量取负后交换 |
| `\` | `(dy, dx)` | 分量直接交换 |

该化简覆盖全部 8 个入射方向，且自然包含两种边界情形：

- **平行滑过**：入射方向与镜面平行时出射等于入射（`/` 镜的 `(1,−1)`、`\` 镜的 `(1,1)`）。
- **垂直返回**：入射方向垂直于镜面时原路返回（`/` 镜的 `(1,1)`、`\` 镜的 `(−1,−1)`）。

不做特殊判断，公式自动给出正确结果 —— 这也是它值得写进单测的原因（T06 / T07）。

### 4.3 元件规则

| 元件 | 出射 |
|---|---|
| 空格 | 一束，方向不变，颜色不变 |
| 反射镜 | 一束，方向按 4.2 变换，颜色不变 |
| 分光镜 | 两束：透射（方向不变）+ 反射（按 4.2），颜色均不变 |
| 棱镜 | 最多三束：把 `color` 拆成 R / G / B 三个分量，各走一个槽位（左转 90° / 直行 / 右转 90°），分量为 0 则不出射 |
| 墙体 | 零束，光被吸收 |
| 目标 | 光终止于此，颜色按位或累加到该目标 |
| 光源 | 起始点，按预设方向与颜色发出 |

棱镜按「掩码拆分 + 槽位路由」实现：入射方向索引 `i`，三个槽位的出射方向分别是
`(i − 2 + 8) % 8`（左转）、`i`（直行）、`(i + 2) % 8`（右转）。
哪个颜色坐哪个槽位由朝向决定，三态轮转（见 4.3.1）。复合色光（如 `Y = R+G`）打上棱镜时
会自然分成两束，不需要额外规则。

**棱镜与分光镜的分界**：分光镜能让**同一种颜色**变成两束（透射 + 反射），棱镜永远不能 ——
每个颜色分量只有一个出口。这是两个元件各自不可替代的地方，也是单测里明确断言的不变量。

#### 4.3.1 朝向的态数由元件决定

`orientStateCount(type)`：反射镜与分光镜 2 态（`/` 与 `\`），棱镜 3 态。
`cycleOrient(type, orient)` 按该元件的态数取模推进，`normalizeOrient(type, orient)`
把外部数据（存档、导入、关卡文件）收敛到合法范围 —— 引擎、存档、关卡校验共用这一个函数，
避免三处各写一遍 `=== BACKSLASH ? ... : ...` 的旧写法。

棱镜三态的语义是**颜色循环序列 `R → G → B` 的起点轮转**：

| 朝向 | 左转 90° | 直行 | 右转 90° |
|---|---|---|---|
| 0 | R | G | B |
| 1 | G | B | R |
| 2 | B | R | G |

渲染层不画「固定朝向的图形」，而是按**实际入射方向**摆三颗色点：从求解结果里取进入该格的
光段算出入射方向，再按上表把三颗点放在真正出射的三个方向上。没有光照到时按「光从左来」画。
这样玩家看到的图永远和光路的实际行为一致。

### 4.4 求解器

- 输入：`level`（关卡定义）+ `placement`（玩家放置的元件）。
- 算法：以所有光源为起点做迭代式光路追踪（工作队列，非递归，避免深光路爆栈）。
- **防环剪枝**：维护 `visited` 集合，键为 `格坐标 + 方向索引 + 颜色掩码`，重复即跳过。
  分光镜构成的环路因此会自然收敛。
- **安全上限**：单次求解最多 4096 个光段，超出即停止并置 `overflow: true`，渲染层给出提示。
- 输出：`{ segments, targets, overflow }`，其中 `segments` 是渲染直接可用的折线段列表。

求解是**纯函数且幂等**：相同输入必须得到逐位相同的输出（T12 断言）。

### 4.5 星级计算

```
stars = 0
if (allTargetsLit) stars = 1
if (stars && placedCount <= level.par + 2) stars = 2
if (stars && placedCount <= level.par)     stars = 3
```

纯函数，输入 `(targets, placedCount, par)`，输出 0–3。与渲染、存档完全解耦。

### 4.6 性能与规模上限（实测）

在 Chromium 1280×800 @ dpr 2（后备缓冲 2560×1600）上实测：

| 场景 | 求解 | 单帧绘制 |
|---|---|---|
| 内置 16 关（最大 12×7） | < 0.005 ms（2000 次批量平均，低于计时器分辨率） | 0.02 ms |
| 几何与元件数上限（40×40 / 998 个分光镜 / 4096 光段） | 6.4 ms | 0.8 ms |

**结论：不需要优化求解器。** 三者同时打满也只有约 7.2 ms，仍在 60 fps 的单帧预算内。
之所以敢这么判定，是因为剪枝键 `格坐标 + 方向 + 颜色` 把状态数钉在
`40 × 40 × 8 × 7 = 89600` 的上界内，工作队列又是迭代式而非递归，不存在爆栈风险。

**`overflow` 不是理论防御**：40×40 铺满分光镜（朝向取 `(x*y)%2` 这类散得开的图案）
时能稳定顶到 4096 段上限。因此它必须有对应的 UI 反馈，不能只置个标记不管 ——
见 6.4 的通关状态行。这一点是阶段 3 复查时补的：引擎会置 `overflow`，
但渲染层与编排层当时都没有消费它，等于玩家会看到一条被截断的光路而毫无提示。

## 五、数据模型

### 5.1 关卡定义

```jsonc
{
  "schema": "light-game/level",
  "version": 1,
  "id": "t01",
  "title": "第一束光",
  "chapter": 0,
  "cols": 10,
  "rows": 8,
  "par": 0,
  "fixed": [
    { "type": "emitter", "x": 1, "y": 4, "dir": 2, "color": 1 },
    { "type": "wall", "x": 5, "y": 2 }
  ],
  "targets": [ { "x": 8, "y": 4, "require": 1 } ],
  "inventory": { "mirror": 0, "splitter": 0, "prism": 0 },
  "hint": "光会一直向右走 —— 把它引到目标上。"
}
```

- `fixed` 里的光源与墙体不可移动、不可删除。
- `targets[].require` 是颜色掩码，入射光的按位或结果满足 `(incoming & require) === require` 即点亮。
- `inventory` 是玩家在该关可用的元件配额，`0` 表示该关不提供此元件。

### 5.2 玩家布局与存档

```jsonc
{
  "schema": "light-game/save",
  "version": 1,
  "stars": { "t01": 3, "t02": 1 },
  "boards": { "t02": [ { "type": "mirror", "x": 3, "y": 4, "orient": 0 } ] },
  "snapshots": [
    { "name": "两条光路", "at": 1758238200000, "levelId": "c03",
      "board": [ { "type": "splitter", "x": 4, "y": 4, "orient": 1 } ] }
  ]
}
```

- `localStorage` 键：`light-game/save`。
- `stars` 与 `boards` 都是**以关卡 id 为键的扁平对象**。星数只记历史最好成绩（`updateStars()`
  返回 `{ save, improved, best }`，只有更优才落盘）；`boards` 是每关的**当前布局**（自动存档），
  布局为空时直接删掉该键，不留空数组。
- `snapshots` 是**一个扁平数组**，不按关分组：每项自带 `levelId`，`at` 是毫秒时间戳。
  上限 `MAX_SNAPSHOTS = 20`，超出时从头 `shift()` 掉最旧的；快照名上限 `MAX_NAME_LENGTH = 24`。
- 存档写入点收敛为两个函数：`rememberBoard()`（布局变化）与 `rememberStars()`（成绩提升），
  避免存档与画面出现两套真值。
- **坏字段丢弃而非整体报废**：`normalizeSave()` 逐字段校验，某关星数非法只丢那一项，
  其余照常读回。只有 `schema` 不符、`version` 非正整数、或版本高于当前实现时才整体退化为空存档。
- 版本迁移位留在 `migrate()`：当前只有 v1，未来按 `while (version < SAVE_VERSION)` 逐级升级。
- `localStorage` 不可用（隐私模式 / 存储被禁 / 受限 `file://`）时 `detectBackend()` 探测失败即
  回落到**内存后端**，本次会话内仍可玩，`store.available` 为假供 UI 提示。

### 5.4 工作台快照的语义

「工作台」是玩家自己攒的布局草稿，与「自动存档」是两件事：

| | 自动存档（`boards`） | 工作台快照（`snapshots`） |
|---|---|---|
| 触发 | 每次布局变化 | 玩家显式点「工作台」保存并命名 |
| 粒度 | 每关一份 | 全局多条，跨关共享 |
| 用途 | 关掉页面回来接着玩 | 试错时的分叉点、成品的收藏 |

导入外部关卡时，若其 `id` 与内置关卡冲突，**只应用 `placement` 布局，不覆盖关卡定义** ——
关卡是骨架（规则与目标不可改），布局才是玩家改出来的东西。

### 5.3 放置元件的运行时表示

```jsonc
{ "type": "splitter", "x": 4, "y": 4, "orient": 0 }   // orient: 0 = `/`，1 = `\`
```

`orient` 只对可旋转元件有意义（`mirror` / `splitter` / `prism`），取值范围由
`orientStateCount(type)` 决定（2 或 3），读取时用 `normalizeOrient(type, orient)` 收敛。

## 六、渲染与交互

### 6.1 场景绘制顺序

```
1. 背景与网格
2. 墙体
3. 目标（含点亮状态与所需颜色提示）
4. 光段折线（在元件之下，避免遮住元件图形）
5. 元件（光源、反射镜、分光镜、棱镜）
6. 光标高亮、拖影、提示文字
```

- 元件图形全部用 Canvas 2D 基础图元绘制，不依赖图片资源。
- 光段颜色由颜色掩码实时映射到具体色值（`R` → 红、`Y` → 黄 …），不预置贴图。
- 网格尺寸由画布尺寸与关卡 `cols`/`rows` 反算，取较小的格边长做正方形格，整体居中，四周留出工具栏与 HUD 的空间。

### 6.2 坐标换算

```
格边长 cell = floor(min(可用宽 / cols, 可用高 / rows))
网格原点 ox = (可用宽 - cell * cols) / 2
           oy = (可用高 - cell * rows) / 2
格 (x, y) 的左上角 = (ox + x * cell, oy + y * cell)
```

全部用**设备像素**参与计算（与骨架阶段保持一致），指针事件拿到的 CSS 像素坐标先乘 dpr 再换算。

### 6.3 输入处理

- 一律 Pointer Events：在 `pointerdown` 里判定目标格与操作意图。指针坐标先乘 dpr，
  再交给 `LightRenderer.pointToCell` 换算成格坐标。
- **判定优先级**（顺序不可换）：选中橡皮 → 删除；该格已有玩家元件 → 旋转；
  该格空且已选中元件 → 放置；该格是关卡预设元件 → 忽略（不可覆盖、不可删除）。
- 触摸端不依赖右键与悬停：删除因此有独立的「橡皮」工具项，而不是靠长按或再次点击。
- 画布区域 `touch-action: none`，禁掉浏览器默认手势干扰。
- 键盘：`1`–`3` 选元件、`E` 选橡皮、方向键移动光标、`Enter` 放置、`R` 切换朝向、
  `Delete` / `Backspace` 删除、`Esc` 取消选中或打开关卡列表（浮层已打开时优先关浮层）。
- **撤销/重做的判定必须排在「带修饰键一律忽略」那一层之前**，否则 `Ctrl+Z` 会被当成
  浏览器快捷键放过去。顺序是：先认 `Ctrl/Cmd+Z`、`Ctrl/Cmd+Shift+Z`、`Ctrl/Cmd+Y`，
  再对剩余的组合键直接 `return`。
- 键盘光标与指针悬停是**同一个高亮概念的两个来源**，共用一份「当前格」状态，两种输入可混用。
- 撤销栈只记录**元件布局的快照**（`{type,x,y,orient}` 数组的克隆），不记录渲染或派生状态，
  保证重做结果确定。上限 `MAX_HISTORY = 100`；产生新操作时砍掉原来的重做分支。
- 清空是**两步确认**（`CLEAR_CONFIRM_MS = 3000` 内再点一次），到点未确认即自动解除武装，
  避免移动端误触把整关布局清光。

- 工具栏**只渲染该关 `inventory` 里配额大于 0 的元件**，末尾附加一个不受配额限制的橡皮。

## 七、文件导入导出

| 能力 | Web 版 | 安卓版（阶段二） |
|---|---|---|
| 导入 | `<input type="file">` + `FileReader`，解析后走统一校验 | 外壳的 `onShowFileChooser` 接管，调用点不变 |
| 导出 | `downloadFile(name, blob)` | **替换为** `window.LightGameAndroid.saveFile(...)` |

导出必须收敛到单一函数，因为 WebView 不支持 `Blob` + `<a download>`。
现在就把调用点收敛好，阶段二只改一个函数体。

**导入校验清单**（任一项不通过即整体拒绝，错误信息指明具体原因与出错下标）：

关卡定义（`levels.validateLevel`）：

1. `schema` 必须等于 `light-game/level`，`version` 必须是 `1`。
2. `id` / `title` 必须是非空字符串，`chapter` 非负整数，`par` 是 `0–999` 的整数。
3. `cols` / `rows` 为整数且落在 `4 ≤ n ≤ 40`（`MIN_SIDE` / `MAX_SIDE`）。
4. `fixed` / `targets` 必须是数组，`inventory` 必须是对象且每项为 `0–999` 的整数。
5. `fixed` 的 `type` 只能在 `core.FIXED_TYPES` 内，坐标 `0 ≤ x < cols`、`0 ≤ y < rows`，
   与已有元件不重叠；光源的 `dir` 必须能换算成 0–7，`color` 是 `1–7` 的整数。
6. `targets[].require` 是 `1–7` 的整数，坐标合法且不重叠。
7. 全部元件总数不超过 `MAX_UNITS = 999`。

玩家布局（`levels.validatePlacement`）：

8. 每项必须是对象，`type` 在**可放置元件白名单**内（`mirror` / `splitter` / `prism`），
   且 `orient` 小于该元件的朝向态数。
9. 坐标是整数且 `0 ≤ x < cols`、`0 ≤ y < rows`；`orient` 只能是 `0` 或 `1`。
10. 不得落在关卡预设元件或目标格上，玩家元件之间也不得自重叠。
11. 每种元件的用量不得超过该关 `inventory` 的配额。

`serializeLevelFile()` 导出的文件 = 关卡定义的原样字段（`LEVEL_FIELDS` 白名单，不打乱字段顺序）
+ 一个 `placement` 字段，与关卡定义共用同一份 schema，因此导入端能一并校验。
内置关卡的 id 快照存在 `BUILTIN_LEVELS`，`registerLevel()` 用它挡住「外部文件覆盖内置关卡定义」，
冲突时只应用布局。

## 八、错误与边界处理

- 画布尺寸为 0（元素被隐藏或尚未布局）时不启动渲染循环，避免空转。
- `getContext("2d")` 失败时静默退出引导，不抛异常污染控制台。
- 求解超过 4096 光段时停止追踪并置 `overflow` 标记，渲染层提示「光路过于复杂」，不冻结页面。
- 存档读取失败（损坏、版本不匹配）时降级到初始状态并提示用户，不静默丢弃数据。
- 导入非法文件时给出明确原因，不做部分导入。
- `localStorage` 不可用（隐私模式）时降级为内存存档，本次会话内仍可玩，仅在退出时提示无法保存。

## 九、兼容性

- 目标视口：360×640 到 1280×800，含 `env(safe-area-inset-*)` 刘海适配。
- 桌面与移动浏览器：Chromium / Firefox / Safari 近期版本。
- 安卓：鸿蒙 4.x（AOSP 双框架）可直接装 APK；纯血鸿蒙 NEXT 不适用，需走 HAP。

**`par` 的验证方式**：每关在 `tests/levels.test.js` 里配一份参考解，测试断言三件事 ——
参考解能通关、元件数正好等于 `par`、去掉参考解中任意一个元件后无法通关。
第三条把 `par` 钉在「局部最优」上，避免关卡被改成随手可过、星级系统失去意义。

局部最优不等于全局最优 —— 12 关设计期间，用一个临时穷举工具按 `par − 1` 搜全解，
两次抓出设计漏洞：`e05` 先后被「两个分光镜一分三」的写法两次破解，最终按实际最小解
把 `par` 改成 2。结论：**新关卡必须过一遍穷举，不能只验参考解**。

**静态校验不替代真实浏览器**：`validateLevel` 只能证明数据结构合法，
`par` 可达性靠求解器验证，而「点得动、看得见」只能靠 `e2e/gameplay.spec.js` 里的真实输入。
历史上有两类问题只有 e2e 抓得到：DOM 数据格式变更后旧选择器失效（`option value` 加了
`builtin:` 前缀），以及「浮层没关就点底栏按钮」这类被遮挡的假死。

CI 两个 job：`node-test`（Node 20.19 / 22.13 / 24 矩阵跑 check + lint + 单测）
与 `browser-smoke`（Node 24 + Chromium 跑 Playwright）。用例编号对应需求文档的 T／U 表。

本地跑 e2e 时产物默认写到系统临时目录（见 `playwright.config.js` 的 `outputDir`）：
本机沙箱会拦截 Playwright 对项目内 `test-results/` 的批量清理，换到临时目录即可绕开。
CI 里仍留在项目内，方便上传 artifact。

**改动 DOM 契约时必须同步 grep**：`option value`、`data-*`、`id` 命名一变，
e2e 与单测里的硬编码就会静默失效（报错信息往往误导到「元素不可见」方向）。
这条纪律来自 `conway-life-game` 项目的一次 19 连红 CI，本项目同样适用。
