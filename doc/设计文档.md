# 光的游戏：设计文档

## 文档信息

| 项目 | 内容 |
|---|---|
| 文档版本 | r2（玩法设计定稿） |
| 对应需求 | `需求与测试用例.md` r2 |
| 当前代码状态 | v0.1.0 工程骨架（`app.js` 仅引导 + 待机占位渲染，**玩法未实现**） |
| 实施策略 | 单页纯静态应用，先 Web 后 APK；工程结构从第一天起按 APK 约束设计 |

## 一、设计目标

1. **零构建**。仓库根目录即 Web 根目录，双击 `index.html` 就能跑，不依赖任何打包产物。
2. **零运行时依赖**。不引框架、不引工具库，浏览器原生能力优先。
3. **可离线**。所有资源本地化，无 CDN、无接口请求。
4. **规则与渲染分离**。玩法纯逻辑可脱离浏览器单测，渲染层不复制任何规则判定。
5. **为 APK 预留接口**。资源同步、文件导出两条链路从第一天就收敛到单点。
6. **触摸与鼠标同源**。统一用 Pointer Events，不为两套输入写两份逻辑。
7. **高分屏与窄屏都正确**。按 DPR 作画，适配刘海安全区与横竖屏。

## 二、总体形态

```
浏览器侧  index.html + styles/main.css + 若干 <script defer> 脚本（共享全局命名空间）
开发侧    scripts/serve-static.js      零依赖静态服务（仅本地与 e2e 使用，不属于应用）
交付侧    仓库根目录即站点根目录，任意静态托管可跑；安卓打包时整目录同步进 assets
```

**为什么不用 ES Module**：阶段二 WebView 通过
`https://appassets.androidplatform.net/assets/index.html` 加载本地资源，
`file://` 与 module 组合会被 CORS 拦截，且 module 的加载时序对纯离线资源不友好。
多文件 + `defer` 顺序加载是这个场景下最稳的方式。

## 三、模块分层

### 3.1 当前（骨架阶段）

| 文件 | 职责 | 依赖 |
|---|---|---|
| `scripts/app.js` | 应用引导：画布、DPR、渲染循环、输入与舞台协调 | 无 |
| `scripts/serve-static.js` | 本地静态服务（开发工具，非应用代码） | 无 |

`app.js` 刻意保持很薄。玩法逻辑按下节拆出去，它只留编排职责。

### 3.2 玩法实现后的拆分

按 `<script defer>` 依赖顺序（**加载顺序即依赖顺序，不可打乱**）：

| # | 文件 | 职责 | 允许依赖 | 可单测 |
|---|---|---|---|---|
| 1 | `scripts/light-core.js` | 8 方向常量、颜色掩码、反射与分光规则、元件规则表 | 无 | ✅ |
| 2 | `scripts/light-engine.js` | 光路求解、目标判定、星级计算 | `light-core` | ✅ |
| 3 | `scripts/levels.js` | 16 关内置关卡数据 + schema 校验函数 | `light-core` | ✅ |
| 4 | `scripts/renderer.js` | 把引擎输出画到 canvas，**不含任何规则判定** | `light-core`（仅取常量） | ❌ |
| 5 | `scripts/storage.js` | `localStorage` 存档、JSON 导入导出、`downloadFile()` | `light-core` | 部分 |
| 6 | `scripts/app.js` | 编排：输入 → 引擎 → 渲染 → HUD → 存档 | 全部 | ❌ |

分层红线（由 `CONTRIBUTING.md` 与代码评审共同保证）：

- `light-core` / `light-engine` 不碰 DOM、不碰 canvas，输入输出都是普通数据结构。
- `renderer` 不复制规则判定，只读引擎给出的结果。
- 随机性必须可注入种子（本游戏目前无需随机，保留该约束以备后续）。

新增脚本后必做三件事：

1. `index.html` 按依赖顺序加 `<script defer>`。
2. `eslint.config.js` 的 `crossScriptGlobals` 补上新的跨文件全局，否则 lint 报 `no-undef`。
3. `package.json` 的 `check` 脚本追加 `node --check scripts/新文件.js`。

### 3.3 已实现的骨架链路

| 机制 | 实现要点 |
|---|---|
| 高分屏 | 后备缓冲 = CSS 尺寸 × `devicePixelRatio`，dpr 封顶 2，避免 4K 屏过度绘制 |
| 尺寸跟随 | `ResizeObserver` 观察画布自身，而非监听 `window.resize` |
| 渲染节流 | 单个 `requestAnimationFrame` 循环；`visibilitychange` 隐藏时取消循环 |
| 动效偏好 | `prefers-reduced-motion` 命中时冻结动画，只画静态画面 |
| 坐标系统 | 以设备像素作画（`canvas.width/height` 即物理像素），不做手工 `ctx.scale`，以免将来与网格坐标换算叠加出二层变换 |
| 调试手柄 | `window.__lightGame` 暴露 `start` / `stop` / `resize`，供 e2e 与控制台使用 |

### 3.4 待机占位渲染的处置

`drawIdleScene()` 是**占位渲染**，只画一个呼吸光晕，用于验证 DPR、resize、动效偏好整条链路。
玩法实现时**整体替换**为真正的场景渲染，不在其上叠加功能。

## 四、核心算法

### 4.1 方向与颜色

**方向**用 8 个索引表示，顺时针排列，配 `(dx, dy)` 增量（屏幕坐标系，y 轴向下）：

| 索引 | 方向 | dx | dy |
|---|---|---|---|
| 0 | 上 | 0 | −1 |
| 1 | 右上 | 1 | −1 |
| 2 | 右 | 1 | 0 |
| 3 | 右下 | 1 | 1 |
| 4 | 下 | 0 | 1 |
| 5 | 左下 | −1 | 1 |
| 6 | 左 | −1 | 0 |
| 7 | 左上 | −1 | −1 |

**颜色**用 3 位掩码：`R=1, G=2, B=4`。合成即按位或，拆分即按位与。

### 4.2 反射规则（本设计的核心，整数运算无浮点误差）

镜面朝向只有两种：`/` 与 `\`，镜面方向的整数向量分别为 `(1,−1)` 与 `(1,1)`。
对入射方向 `(dx, dy)`，出射方向可由镜像公式化简为**纯整数交换**：

| 镜面 | 出射方向 | 说明 |
|---|---|---|
| `/` | `(−dy, −dx)` | 分量取负后交换 |
| `\` | `(dy, dx)` | 分量直接交换 |

该化简覆盖全部 8 个入射方向，且自然包含两种边界情形：

- **平行滑过**：入射方向与镜面平行时出射等于入射（`/` 镜的 `(1,−1)`、`\` 镜的 `(1,1)`）。
- **垂直返回**：入射方向垂直于镜面时原路返回（`/` 镜的 `(1,1)`、`\` 镜的 `(−1,−1)`）。

不做特殊判断，公式自动给出正确结果 —— 这也是它值得写进单测的原因（T06 / T07）。

### 4.3 元件规则

| 元件 | 出射 |
|---|---|
| 空格 | 一束，方向不变，颜色不变 |
| 反射镜 | 一束，方向按 4.2 变换，颜色不变 |
| 分光镜 | 两束：透射（方向不变）+ 反射（按 4.2），颜色均不变 |
| 二向色镜(c) | 最多两束：反射束颜色 `color & c`、透射束颜色 `color & ~c`；某束颜色为 0 则不出射 |
| 墙体 | 零束，光被吸收 |
| 目标 | 光终止于此，颜色按位或累加到该目标 |
| 光源 | 起始点，按预设方向与颜色发出 |

二向色镜用「掩码拆分」而非「按颜色相等判断」，因此复合色光（如 `Y = R+G`）打上红二向色镜时
会自然分成反射的红光与透射的绿光 —— 颜色拆分机制不需要额外规则。

### 4.4 求解器

- 输入：`level`（关卡定义）+ `placement`（玩家放置的元件）。
- 算法：以所有光源为起点做迭代式光路追踪（工作队列，非递归，避免深光路爆栈）。
- **防环剪枝**：维护 `visited` 集合，键为 `格坐标 + 方向索引 + 颜色掩码`，重复即跳过。
  分光镜构成的环路因此会自然收敛。
- **安全上限**：单次求解最多 4096 个光段，超出即停止并置 `overflow: true`，渲染层给出提示。
- 输出：`{ segments, targets, overflow }`，其中 `segments` 是渲染直接可用的折线段列表。

求解是**纯函数且幂等**：相同输入必须得到逐位相同的输出（T12 断言）。

### 4.5 星级计算

```
stars = 0
if (allTargetsLit) stars = 1
if (stars && placedCount <= level.par + 2) stars = 2
if (stars && placedCount <= level.par)     stars = 3
```

纯函数，输入 `(targets, placedCount, par)`，输出 0–3。与渲染、存档完全解耦。

## 五、数据模型

### 5.1 关卡定义

```jsonc
{
  "schema": "light-game/level",
  "version": 1,
  "id": "t01",
  "title": "第一束光",
  "chapter": 0,
  "cols": 10,
  "rows": 8,
  "par": 0,
  "fixed": [
    { "type": "emitter", "x": 1, "y": 4, "dir": 2, "color": 1 },
    { "type": "wall", "x": 5, "y": 2 }
  ],
  "targets": [ { "x": 8, "y": 4, "require": 1 } ],
  "inventory": { "mirror": 0, "splitter": 0, "dichroicR": 0, "dichroicG": 0, "dichroicB": 0 },
  "hint": "光会一直向右走 —— 把它引到目标上。"
}
```

- `fixed` 里的光源与墙体不可移动、不可删除。
- `targets[].require` 是颜色掩码，入射光的按位或结果满足 `(incoming & require) === require` 即点亮。
- `inventory` 是玩家在该关可用的元件配额，`0` 表示该关不提供此元件。

### 5.2 玩家布局与存档

```jsonc
{
  "schema": "light-game/save",
  "version": 1,
  "progress": { "t01": { "stars": 3, "bestCount": 0 }, "t02": { "stars": 1, "bestCount": 4 } },
  "boards":   { "t02": [ { "type": "mirror", "x": 3, "y": 4, "orient": 0 } ] },
  "snapshots": { "t02": [ { "name": "两条光路", "at": "2026-09-19T04:50:00Z", "board": [] } ] }
}
```

- `localStorage` 键：`light_game/save/v1`。
- `boards` 是每关的**当前布局**（自动存档），`progress` 是历史最好成绩。
- `snapshots` 是手动保存的具名工作台快照。
- 存档格式一旦随正式版发布，变更必须提供迁移路径；读取失败时降级到初始状态并提示用户，不静默丢弃。

### 5.3 放置元件的运行时表示

```jsonc
{ "type": "splitter", "x": 4, "y": 4, "orient": 0 }   // orient: 0 = `/`，1 = `\`
```

`orient` 只对可旋转元件有意义（`mirror` / `splitter` / `dichroic*`）。

## 六、渲染与交互

### 6.1 场景绘制顺序

```
1. 背景与网格
2. 墙体
3. 目标（含点亮状态与所需颜色提示）
4. 光段折线（在元件之下，避免遮住元件图形）
5. 元件（光源、反射镜、分光镜、二向色镜）
6. 光标高亮、拖影、提示文字
```

- 元件图形全部用 Canvas 2D 基础图元绘制，不依赖图片资源。
- 光段颜色由颜色掩码实时映射到具体色值（`R` → 红、`Y` → 黄 …），不预置贴图。
- 网格尺寸由画布尺寸与关卡 `cols`/`rows` 反算，取较小的格边长做正方形格，整体居中，四周留出工具栏与 HUD 的空间。

### 6.2 坐标换算

```
格边长 cell = floor(min(可用宽 / cols, 可用高 / rows))
网格原点 ox = (可用宽 - cell * cols) / 2
           oy = (可用高 - cell * rows) / 2
格 (x, y) 的左上角 = (ox + x * cell, oy + y * cell)
```

全部用**设备像素**参与计算（与骨架阶段保持一致），指针事件拿到的 CSS 像素坐标先乘 dpr 再换算。

### 6.3 输入处理

- 一律 Pointer Events：`pointerdown` 判定目标格与操作意图，`pointerup` 提交。
- 触摸端不依赖右键与悬停。次要操作（删除、旋转）通过工具栏按钮或「再次点击同一元件」实现。
- 画布区域 `touch-action: none`，禁掉浏览器默认手势干扰。
- 键盘：`1`–`5` 选元件、方向键移动光标、`Enter` 放置、`R` 旋转、`Delete` 删除、`Ctrl+Z` / `Ctrl+Shift+Z` 撤销重做、`Esc` 返回。
- 撤销栈只记录**元件布局的快照**（浅拷贝的数组），不记录渲染或派生状态，保证重做结果确定。

### 6.4 HUD

| 区域 | 内容 |
|---|---|
| 顶栏 | 关卡编号与名称、当前星数 / 3、返回按钮 |
| 工具栏 | 各元件图标 + 剩余配额、撤销 / 重做 / 清空 / 保存 / 导入 / 导出 |
| 浮层 | 通关结算（星数、使用元件数、下一关按钮）；导入失败提示 |

## 七、文件导入导出

| 能力 | Web 版 | 安卓版（阶段二） |
|---|---|---|
| 导入 | `<input type="file">` + `FileReader`，解析后走统一校验 | 外壳的 `onShowFileChooser` 接管，调用点不变 |
| 导出 | `downloadFile(name, blob)` | **替换为** `window.LightGameAndroid.saveFile(...)` |

导出必须收敛到单一函数，因为 WebView 不支持 `Blob` + `<a download>`。
现在就把调用点收敛好，阶段二只改一个函数体。

**导入校验清单**（任一项不通过即整体拒绝，错误信息指明具体原因）：

1. `schema` 必须等于 `light-game/level`，`version` 必须是已知版本。
2. `cols` / `rows` 为整数且落在 `4 ≤ n ≤ 40`。
3. 所有坐标 `0 ≤ x < cols`、`0 ≤ y < rows`，且不在 `fixed` 占用格上。
4. `type` 必须在白名单内。
5. `dir` ∈ 0–7，`color` / `require` 是 `1–7` 的整数，`orient` ∈ {0, 1}。
6. 元件总数与 `inventory` 各项均不超过 999。

## 八、错误与边界处理

- 画布尺寸为 0（元素被隐藏或尚未布局）时不启动渲染循环，避免空转。
- `getContext("2d")` 失败时静默退出引导，不抛异常污染控制台。
- 求解超过 4096 光段时停止追踪并置 `overflow` 标记，渲染层提示「光路过于复杂」，不冻结页面。
- 存档读取失败（损坏、版本不匹配）时降级到初始状态并提示用户，不静默丢弃数据。
- 导入非法文件时给出明确原因，不做部分导入。
- `localStorage` 不可用（隐私模式）时降级为内存存档，本次会话内仍可玩，仅在退出时提示无法保存。

## 九、兼容性

- 目标视口：360×640 到 1280×800，含 `env(safe-area-inset-*)` 刘海适配。
- 桌面与移动浏览器：Chromium / Firefox / Safari 近期版本。
- 安卓：鸿蒙 4.x（AOSP 双框架）可直接装 APK；纯血鸿蒙 NEXT 不适用，需走 HAP。
