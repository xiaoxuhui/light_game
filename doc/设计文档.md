# 光的游戏：设计文档

## 文档信息

| 项目 | 内容 |
|---|---|
| 版本 | v0.1.0（工程骨架） |
| 状态 | **骨架已落地，玩法部分待需求定稿后补齐** |
| 实施策略 | 单页纯静态应用，先 Web 后 APK；工程结构从第一天起按 APK 约束设计 |
| 对应需求 | `需求与测试用例.md` |

## 一、设计目标

1. **零构建**。仓库根目录即 Web 根目录，双击 `index.html` 就能跑，不依赖任何打包产物。
2. **零运行时依赖**。不引框架、不引工具库，浏览器原生能力优先。
3. **可离线**。所有资源本地化，无 CDN、无接口请求。
4. **规则与渲染分离**。玩法纯逻辑可脱离浏览器单测，渲染层不复制任何规则判定。
5. **为 APK 预留接口**。资源同步、文件导出两条链路从第一天就收敛到单点。
6. **触摸与鼠标同源**。统一用 Pointer Events，不为两套输入写两份逻辑。
7. **高分屏与窄屏都正确**。按 DPR 作画，适配刘海安全区与横竖屏。

## 二、总体形态

```
浏览器侧  index.html + styles/main.css + 若干 <script defer> 脚本（共享全局命名空间）
开发侧    scripts/serve-static.js      零依赖静态服务（仅本地与 e2e 使用，不属于应用）
交付侧    仓库根目录即站点根目录，任意静态托管可跑；安卓打包时整目录同步进 assets
```

**为什么不用 ES Module**：阶段二 WebView 通过
`https://appassets.androidplatform.net/assets/index.html` 加载本地资源，
`file://` 与 module 组合会被 CORS 拦截，且 module 的加载时序对纯离线资源不友好。
多文件 + `defer` 顺序加载是这个场景下最稳的方式。

## 三、模块分层

### 3.1 当前（骨架阶段）

| 文件 | 职责 | 依赖 |
|---|---|---|
| `scripts/app.js` | 应用引导：画布、DPR、渲染循环、输入与舞台协调 | 无 |
| `scripts/serve-static.js` | 本地静态服务（开发工具，非应用代码） | 无 |

`app.js` 刻意保持很薄。玩法逻辑一旦确定，按下节拆出去，它只留编排职责。

### 3.2 玩法实现后的预期拆分

按 `<script defer>` 依赖顺序：

```
1. scripts/light-engine.js        纯计算：光路求解、元件规则。无 DOM、无 canvas，可单测
2. scripts/renderer.js            纯绘制：把引擎状态画到 canvas，不含任何规则判定
3. scripts/<关卡或编辑器>.js       内容组织与编辑交互
4. scripts/app.js                 编排：输入 → 引擎 → 渲染 → HUD
```

分层红线（由 `CONTRIBUTING.md` 与代码评审共同保证）：

- 引擎不碰 DOM、不碰 canvas，输入输出都是普通数据结构。
- 渲染层不复制规则判定，只读引擎给出的结果。
- 随机性必须可注入种子。

新增脚本后必做三件事：

1. `index.html` 按依赖顺序加 `<script defer>`。
2. `eslint.config.js` 的 `crossScriptGlobals` 补上新的跨文件全局，否则 lint 报 `no-undef`。
3. `package.json` 的 `check` 脚本追加 `node --check scripts/新文件.js`。

### 3.3 已实现的骨架链路

| 机制 | 实现要点 |
|---|---|
| 高分屏 | 后备缓冲 = CSS 尺寸 × `devicePixelRatio`，dpr 封顶 2，避免 4K 屏过度绘制 |
| 尺寸跟随 | `ResizeObserver` 观察画布自身，而非监听 `window.resize` |
| 渲染节流 | 单个 `requestAnimationFrame` 循环；`visibilitychange` 隐藏时取消循环 |
| 动效偏好 | `prefers-reduced-motion` 命中时冻结脉冲动画，只画静态画面 |
| 坐标系统 | 以设备像素作画（`canvas.width/height` 即物理像素），不做手工 `ctx.scale`，以免将来与网格／物理坐标换算叠加出二层变换 |
| 调试手柄 | `window.__lightGame` 暴露 `start` / `stop` / `resize`，供 e2e 与控制台使用 |

### 3.4 待机占位渲染

`drawIdleScene()` 是**占位渲染**，只画一个呼吸光晕，用于验证 DPR、resize、动效偏好整条链路。
玩法定稿后整体替换为真正的场景渲染，**不要在其上继续叠加功能**。

## 四、状态与数据模型

待玩法定稿后填写。已知约束：

- 运行时持久化走 `localStorage`（安卓 WebView 外壳已规划开启 `domStorageEnabled`，
  并用固定域名加载以保证 origin 稳定）。
- 存档格式一旦发布就必须保持向后兼容；格式变更需要设计并测试迁移路径。
- 导入文件必须完整校验（结构、类型、取值范围、规模上限），不信任文件内容。

## 五、接口与控制

待玩法定稿后填写。已知约束：

- 一律 Pointer Events，鼠标与触摸同源。
- 键盘可用性在桌面端必须保证（方向键／空格等常规约定）。
- 画布区域 `touch-action: none`，禁掉浏览器默认手势干扰。

## 六、文件导入导出

| 能力 | Web 版 | 安卓版（阶段二） |
|---|---|---|
| 导入 | `<input type="file">` | 外壳的 `onShowFileChooser` 接管，调用点不变 |
| 导出 | `downloadFile(name, blob)` | **替换为** `window.LightGameAndroid.saveFile(...)` |

导出必须收敛到单一函数，因为 WebView 不支持 `Blob` + `<a download>`。
现在就把调用点收敛好，阶段二只改一个函数体。

## 七、错误与边界处理

- 画布尺寸为 0（元素被隐藏或尚未布局）时不启动渲染循环，避免空转。
- `getContext("2d")` 失败时静默退出引导，不抛异常污染控制台。
- 存档读取失败（损坏、版本不匹配）时降级到初始状态并提示用户，不静默丢弃数据。
- 导入非法文件时给出明确原因，不做部分导入。

## 八、兼容性

- 目标视口：360×640 到 1280×800，含 `env(safe-area-inset-*)` 刘海适配。
- 桌面与移动浏览器：Chromium / Firefox / Safari 近期版本。
- 安卓：鸿蒙 4.x（AOSP 双框架）可直接装 APK；纯血鸿蒙 NEXT 不适用，需走 HAP。
- 存档格式：发布后不破坏兼容；必须变更时提供迁移。

## 九、测试策略

| 层 | 文件 | 覆盖内容 |
|---|---|---|
| 结构断言 | `tests/static-app.test.js` | 版本一致、资源引用存在且相对、脚本 defer 与无 module、门禁文件齐全、端口一致 |
| 单元测试 | `tests/*.test.js` | 引擎纯函数、存档往返、导入拒绝路径（玩法实现后新增） |
| 浏览器冒烟 | `e2e/app.smoke.spec.js` | 页面可加载、画布初始化、真实绘制、resize 跟随、控制台干净、调试手柄 |

CI 两个 job：`node-test`（Node 20.19 / 22.13 / 24 矩阵跑 check + lint + 单测）
与 `browser-smoke`（Node 24 + Chromium 跑 Playwright）。用例编号对应需求文档的 T／U 表。
